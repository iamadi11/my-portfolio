The installed Eidos 2.5.2 implementation was inspected directly: `dist/types.d.ts` queue entries have no result field; `dist/action.js` treats any resolved replay as succeeded and removes it after three seconds. A queue status therefore cannot establish the contact API outcome. Receipts contain only the last 12 ids/outcomes, not email/message bodies; they use a memory fallback when storage is unavailable. Missing, old, corrupt or unavailable receipts remain unconfirmed. The server's existing idempotency retention is seven days; no exactly-once or unlimited delivery guarantee was added.
